# StateRecovery

Keeps clients' grids in sync with the server, and repairs a client whose grid fell out of sync.

**The bug.** A grid that loses the same chunk twice before every player acks the first loss (a ship breaking up as it
lands, wrecks grinding together) gets that chunk twice in its engine-side `ChunkDeletionHistory`. RobustToolbox's
`OnGridGetState` then throws on the duplicate, and since grids are sent to everyone, every player's game state fails
that tick. With no state built, the engine thinks no one is connected and wipes all deletion history, so clients keep
the dead chunk. The next time the grid's fixtures are resent, the dead chunk names fixtures that no longer exist and
client physics throws `KeyNotFoundException` (`grid_chunk-...`) every tick until the player reconnects.

**Server.** `WFGridDeletionHistorySystem.Dedupe` runs from `EntryPoint`'s `PostEngine` update, after every system and
before game states are built, and keeps only the newest entry per chunk (the field is internal, so it uses
reflection and logs an error at startup if the engine changes it). Remove it once the engine handles duplicates.

**Client.** `WFStateRecoverySystem` watches each physics step: a `PhysicsUpdateBeforeSolveEvent` with no matching
`PhysicsUpdateAfterSolveEvent` means the step threw on the way. If 10 or more steps fail within 2 seconds, the client
asks the server for a full game state (what `fullstatereset` does). Requests back off from 30 seconds to 5 minutes,
and the back-off resets after 5 quiet minutes. `Requests` counts them (View Variables). This catches any other desync
that breaks physics the same way.
